# Canonical Data Contract

**Document:** Santis OS Architecture Book  
**Volume:** 1 – Architecture Principles  
**Version:** 0.9-RC2  
**Status:** Normative Draft

---

# Purpose

This document defines the minimum identity, ownership, versioning, lifecycle, audit, and recovery requirements for authoritative Santis OS records.

The contract does not require every table or record type to contain identical columns. Each record type MUST implement the contract sections applicable to its scope and behavior.

This document distinguishes canonical state from projections, caches, analytics models, search indexes, interface views, and migration artifacts.

---

# Normative Scope

This contract applies to:

- canonical PostgreSQL entities;
- canonical command and aggregate identities;
- tenant-scoped operational records;
- financial and entitlement records;
- append-only ledgers and audit records where applicable;
- projection metadata required to reconcile derived systems with the canonical source.

Global reference catalogs, ephemeral technical records, and value-object-only structures MAY implement a reduced profile where explicitly documented.

---

# Contract Profiles

The Canonical Data Contract consists of three profiles.

A record MUST implement Profile A.

A tenant-scoped operational record MUST also implement Profile B.

A record MUST implement applicable Profile C fields according to its lifecycle and business semantics.

---

# Profile A — Universal Canonical Metadata

Every canonical entity MUST contain the following logical fields or equivalent guaranteed metadata:

| Field | Requirement | Purpose |
|---|---|---|
| `id` | MUST | Immutable canonical identifier |
| `created_at` | MUST | Canonical creation timestamp |
| `created_by_actor_id` | MUST | Actor responsible for creation |
| `trace_id` | MUST | End-to-end operation trace identity |
| `contract_version` | MUST | Data-contract version used to interpret the record |

## A.1 Immutable Identifier

The canonical `id` MUST be immutable after creation.

Display names, external record IDs, Airtable record IDs, email addresses, phone numbers, human-readable codes, and compound labels MUST NOT replace the canonical identifier.

External system identifiers MAY be stored as mappings, but MUST NOT become the sole canonical identity unless an approved ADR explicitly establishes that external system as authority.

## A.2 Creation Time

`created_at` MUST be generated by an authoritative server or database clock.

Client-provided creation timestamps MUST NOT be accepted as authoritative creation time.

Business occurrence time MAY be stored separately as `occurred_at` or `effective_at`.

## A.3 Actor Identity

`created_by_actor_id` MUST identify a resolvable actor record.

Actor types MAY include:

- human user;
- service account;
- automation;
- migration process;
- integration;
- AI agent acting under delegated authority.

An actor display name MUST NOT be used as the sole audit identity.

## A.4 Trace Identity

`trace_id` MUST allow the record to be associated with the command, transaction, audit event, outbox event, worker execution, or integration call that created it.

Trace identity MUST NOT be treated as the canonical business identifier.

## A.5 Contract Version

`contract_version` MUST identify the schema and interpretation contract applicable to the record.

Readers MUST reject unsupported breaking versions or route them through an approved compatibility adapter.

# Profile B — Tenant-Scoped Operational Context

A tenant-scoped operational entity MUST include the following logical fields where applicable:

| Field | Requirement | Purpose |
|---|---|---|
| `tenant_id` | MUST | Tenant ownership and isolation boundary |
| `location_id` or approved scope reference | MUST when location-scoped | Physical or logical operating scope |
| `aggregate_version` or `row_version` | MUST for mutable aggregates | Optimistic concurrency control |
| `lifecycle_state` | MUST where the entity has a state machine | Current canonical lifecycle state |

## B.1 Tenant Ownership

Every tenant-scoped record MUST have exactly one canonical `tenant_id`.

Tenant ownership MUST NOT be inferred solely through a chain of optional relationships at authorization time when the record can carry tenant ownership directly.

A tenant-scoped foreign relationship MUST NOT link records belonging to different tenants.

Database constraints SHOULD enforce tenant consistency through composite keys or equivalent constraints where practical.

## B.2 Location or Scope

A location-scoped operational record MUST carry a canonical `location_id`.

A record that is intentionally broader or narrower than a location MAY use an approved scope model such as:

- `scope_type` plus `scope_id`;
- legal entity scope;
- organization scope;
- department scope.

Display labels and branch codes MUST NOT replace exact scope identifiers.

## B.3 Concurrency Version

Mutable canonical aggregates MUST expose an `aggregate_version` or `row_version` used to prevent lost updates.

The version MUST increase atomically with successful state changes.

A stale expected version MUST cause a controlled concurrency conflict.

`source_version` SHOULD be reserved for projections and external-source synchronization metadata and SHOULD NOT be used as the canonical aggregate concurrency field.

## B.4 Lifecycle State

Entities with business state transitions MUST expose a canonical `lifecycle_state`.

Lifecycle transitions MUST be performed through approved domain commands.

Direct free-form editing of lifecycle values is prohibited.

The allowed transitions MUST be documented in a state-machine contract.

# Profile C — Record-Type-Specific Metadata

Depending on the record type, one or more of the following fields MAY or MUST apply:

| Field | Typical applicability |
|---|---|
| `updated_at` | Mutable canonical records |
| `updated_by_actor_id` | Mutable canonical records |
| `deleted_at` | Soft-deletion policy where approved |
| `effective_at` | Policy, price, entitlement, or accounting effectiveness |
| `occurred_at` | Business-event occurrence time |
| `reversal_of_id` | Reversal or correction records |
| `supersedes_id` | Replacement records |
| `reconciliation_status` | Financial or projection reconciliation |
| `external_source_id` | Mapping to an external authority or migration source |
| `external_source_version` | Version from an external source |
| `retention_class` | Data-retention policy classification |
| `data_classification` | PII, financial, operational, security, or public classification |

## C.1 Mutable Records

Mutable canonical records SHOULD include:

- `updated_at`;
- `updated_by_actor_id`.

Updates MUST preserve audit evidence and concurrency safety.

## C.2 Append-Only Records

Append-only records MUST NOT be modified to rewrite historical facts.

Append-only financial, audit, event, and ledger records SHOULD omit mutable update semantics.

Corrections MUST be represented through an approved correction, reversal, supersession, or adjustment record.

## C.3 Deletion

Canonical deletion MUST be governed by data classification, legal retention, audit, and domain rules.

Hard deletion MUST NOT be the default for financial, audit, entitlement, booking-history, or security evidence.

Soft deletion MUST NOT be used to conceal a business reversal that requires an explicit domain record.

# Canonical State

Canonical state is the authoritative operational truth for its owning bounded context.

Canonical state MAY only change through:

- approved domain commands;
- approved migrations;
- approved reconciliation or correction commands;
- controlled restoration procedures.

Direct production table editing outside approved procedures is prohibited.

Canonical state MUST NOT be reconstructed from projections alone.

---

# Source-of-Truth Allocation

The target source-of-truth model is:

```text
PostgreSQL
→ Canonical authority and transaction-safe persistence

Modular backend
→ Authorization, command orchestration, domain decisions and audit

React and approved clients
→ User interaction and command submission

Airtable
→ Transitional intake, projection, QA, evidence and governance
```

During controlled migration, Airtable MAY temporarily remain authoritative for explicitly listed capabilities.

Any temporary Airtable authority MUST be recorded in the Architecture Status Matrix and Authority Matrix with:

- capability;
- authoritative table and fields;
- owner;
- migration status;
- replacement contract;
- retirement gate.

Authority MUST NOT be ambiguous.

---

# Environment Boundary

Production and non-production data SHOULD be physically separated into different databases or equivalent isolated environments.

The `environment` field MAY remain necessary in:

- Airtable transition records;
- test fixtures;
- projection metadata;
- controlled migration evidence;
- systems that intentionally share an approved physical boundary.

An `environment` column MUST NOT be treated as a substitute for physical production isolation.

The final environment strategy MUST be governed by the relevant ADR.

---

# Ownership

Each canonical entity MUST have exactly one owning bounded context.

The owning bounded context is responsible for:

- lifecycle rules;
- canonical schema;
- accepted commands;
- domain invariants;
- published events;
- correction and recovery procedures.

Other bounded contexts MUST NOT directly mutate the owning context’s canonical tables.

Synchronous access MUST use a published application interface.

Completed facts SHOULD be shared through approved domain events or projections.

---

# Relationships and Referential Integrity

Canonical relationships MUST use exact identifiers.

Where a relationship is tenant-scoped, the database SHOULD enforce tenant consistency through composite uniqueness and foreign keys or an equivalent integrity mechanism.

A canonical relationship MUST NOT be established through display-name matching, fuzzy matching, or unverified text codes.

Unresolved relationship cardinality MUST fail closed or enter quarantine.

---

# Versioning

Breaking changes to canonical record interpretation MUST increment `contract_version`.

Backward-compatible additions MAY retain the current version when consumers can safely ignore the new fields.

Version changes MUST include:

- migration strategy;
- compatibility policy;
- consumer impact analysis;
- rollback or recovery boundary;
- contract tests.

Contract versioning MUST NOT be used to conceal parallel competing authority fields.

---

# Projection Contract

A projection is a derived, disposable representation of canonical state.

Every durable external projection SHOULD include:

- `source_system`;
- `source_record_id`;
- `source_version`;
- `projection_contract_version`;
- `projected_at`;
- `reconciliation_status`;
- `projection_error` where applicable.

Projection consumers MUST tolerate defined projection delay.

A stale or failed projection MUST NOT silently replace the canonical state.

Projection reconciliation MUST compare exact canonical identifiers and versions.

---

# Recovery

Canonical state MAY be recovered only through controlled procedures, including:

- encrypted backup restoration;
- point-in-time recovery;
- approved durable command replay;
- approved event-based rebuilding where the event source is itself canonical and complete;
- verified migration rollback or forward correction.

Projection rebuilding is not canonical recovery.

A recovery procedure MUST preserve or reconstruct:

- tenant ownership;
- canonical identifiers;
- aggregate versions;
- audit linkage;
- financial and entitlement integrity;
- command and event correlation where available.

---

# Compliance and Exceptions

Every new canonical entity MUST identify which contract profiles it implements.

A deviation MUST be documented in an approved ADR, schema contract, or temporary exception containing:

- rationale;
- risk;
- compensating controls;
- owner;
- review date;
- removal or permanent-approval condition.

A table existing in PostgreSQL or Airtable does not automatically make it canonical.

Canonical status MUST be explicitly declared in the Architecture Status Matrix and bounded-context ownership map.
